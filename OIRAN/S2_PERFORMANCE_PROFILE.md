## Observable work and anti-elision

Every full/processing packet is fingerprint-checked and parsed. Workers fold decoded TEIDs and packet numbers into an ordered `work_accumulator`. Packet-number sum/XOR and generated/processed/drop invariants are checked before a successful result is returned. Generator-only mode folds every generated frame fingerprint into its accumulator. These externally printed values prevent the benchmarked work from being optimized away.

## Measurement definitions

- Payload throughput: bytes after Ethernet + outer IPv4 + UDP + mandatory GTP-U header (50 captured bytes excluded).
- Captured throughput: complete generated byte slice length.
- Ethernet wire-rate equivalent: captured length plus FCS (4), preamble/SFD (8) and inter-frame gap (12).
- CPU: process user+system CPU time divided by elapsed wall time; values above 100% represent multiple logical cores.
- Queue occupancy: per-worker queued batch plus transient receiver handoff; aggregate output sums worker high-watermarks.

## Generator limitation determination

Generator limitation is strongly indicated, but not independently quantified:

1. A one-worker run consumes close to two logical cores, matching producer + worker activity.
2. Worker scaling is 52.94%, 33.07%, and 22.88% efficient at 2/3/4 workers on the selected profile.
3. Larger batches improve throughput by reducing per-batch overhead, while extra workers do not.
4. Small-frame one-worker tests can overrun the consumer, proving the balance changes by frame/batch profile.

The planned A/B/C runs are the required next diagnostic step once production stability is confirmed. Until then, packet generation, integrity scanning and allocation are `INFERRED` as the leading bottleneck rather than isolated certified percentages.
